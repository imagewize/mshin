## General Rules

### 1. Read Before You Act

Before changing a file, read:
- The file itself, end to end
- Whatever calls it (`servers/src/kali/index.js` for tools, `clients/mshin-cli/index.js` for the agent loop)
- The docs that describe the behaviour you are changing

**Never edit a file you have not read in the current session.**

### 2. Change Minimally

- Touch only what the task requires
- Do not refactor or reformat unrelated code
- Do not rename variables or functions unless asked
- Match the surrounding style (indentation, naming, error handling)

### 3. Prove It Works

You are **not done** when the edit lands, the syntax parses, or the code looks right. You are done when the acceptance criterion is met and you can point at the evidence.

For this repo that usually means:
- `npm test` in `servers/src/kali/` and `clients/mshin-cli/` (see [Testing](#testing) for what that does and does not cover)
- A documented command actually run, or explicitly flagged as unverified
- For MCP changes: the server starts, `curl :3000/health` answers, and the tool appears in `tools/list`

State plainly which of these you did. Do not claim "tested" or "verified" for a step you skipped.

### 4. Git Workflow

**Commit messages:**
- Imperative mood ("Add feature", not "Added feature")
- First line 50 characters or less
- Body explains what and why, when it is not obvious
- Conventional-commit prefixes where they fit (`feat:`, `fix:`, `docs:`, `refactor:`, `chore:`)
- **No attribution footers** of any kind — no `Co-Authored-By`, no "Generated by" trailers

**Branches:**
- `feature/`, `fix/`, `docs/`, `refactor/`, `chore/` + short description
- One logical change per branch

**Require explicit user approval:**
- `git push` (state the branch when asking)
- Force-push — and prefer `--force-with-lease`
- `git reset --hard`, `git clean -fd`, `rm`, `git rm`
- Never push to `main` or `release/*`

### 5. Security Considerations

This repo ships offensive tooling. Be careful:
- Never commit secrets, API keys, or credentials
- Never include a real third-party target IP or domain in an example
- Document only legal use against systems the reader owns or is authorised to test
- Keep configurations secure by default

## Repo Invariants

These break silently if you are careless. Check them on every relevant change.

### The tool list lives in five places

Adding, removing, or renaming an MCP tool means updating **all** of these, or the Node ships a tool it cannot run — or refuses one it can:

1. `servers/src/kali/tools.js` — the definition, its `TOOL_PATHS` entry, and its handler
2. `scripts/setup_mcp_server.sh` — the `--tools` flag **and** the apt package list
3. `scripts/setup_mcp_server.sh` — the `NOPASSWD` sudoers allowlist for the `mshin` user
4. `configs/mcp-kali.service` — the `--tools` flag in `ExecStart`
5. `configs/ollama-modelfile` — the documented tool list in the system prompt

Under the **Docker deployment** (`configs/Dockerfile`), points 2 and 3 collapse into the image: the apt list becomes the `KALI_TOOLS` build arg, and there is no sudoers entry at all — the container needs no sudo. The `--tools` list still appears once more in the Dockerfile's `CMD`, so a tool change touches `KALI_TOOLS` **and** `CMD` there. See [Docker Local Dev](docs/DOCKER-LOCAL-DEV.md).

The sudoers entry is the one people forget. `servers/src/kali/tools.js` runs every binary as `sudo -n` when the process is not root, so a tool missing from the allowlist fails at runtime with `sudo: a password is required`, not at startup.

`lima/mshin-node.yaml` mirrors three of the five for the Lima path: its apt install list stands in for the setup script's, and its sudoers block and unit `sed` line for the `--tools` flag. A tool change touches all three there too.

### Docs cross-reference each other

If you add, move, or rename a file, update:
- `README.md` — the Documentation list
- `CONTRIBUTING.md` — the Project Structure tree
- The table in [Canonical sources](#canonical-sources) above

### Network defaults are fixed by convention

Examples across the repo use `192.168.1.100` (Node), `192.168.1.200` (Core), `192.168.1.1` (gateway), and port `3000`. Lima guests use Lima's shared vmnet range, `192.168.105.0/24`. Do not invent new addresses; do not swap these for RFC 5737 documentation ranges. **Scan targets** are different — those must be `127.0.0.1` or an RFC 5737 range (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`), never a real host.

## File-Specific Guidelines

### Documentation (`docs/`, root `*.md`)

**Style:**
- ATX headers (`#`, `##`)
- Backticks for code, commands, filenames; **bold** for key terms; `>` blockquotes for asides
- Wheel of Time epigraphs and theming are deliberate house style — preserve the tone

**Structure:** quote, overview, prerequisites, setup, usage, troubleshooting, changelog.

**Content:**
- Link to other docs rather than duplicating them
- Placeholders for anything reader-specific: `<NODE_IP>`, `<PATH>`, `<PASSWORD>` — never a real home directory
- Run the commands you document, or say which ones you could not
- Verify CLI syntax against the installed version rather than memory; flags change between major releases
- ASCII diagrams must have every line the same display width

### Configuration (`configs/`)

Follow the existing format exactly. `mcp-kali.service` is a real systemd unit with hardening directives (`ProtectSystem`, `ReadWritePaths`) — changing paths there means changing those too.

### Scripts (`scripts/`)

- Executable, `#!/bin/bash` shebang, `set -euo pipefail`
- Usage comments at the top
- Absolute paths
- Idempotent where practical: these get re-run on half-provisioned machines

### Code (`servers/`, `clients/`)

- 4-space indent for shell and Python; 2-space for YAML and JSON
- Node 20+, ESM (`"type": "module"`)
- No new runtime dependencies without discussion
- Argument values reaching a tool must stay inside the `assertSafe` guards in `servers/src/kali/tools.js`

## Tool Usage

### Shell

- Absolute paths
- Timeouts on anything that can hang (`timeout 30s ...`)
- Do not leave servers, watchers, or other long-running processes running in the background when you finish; if you start one to test, stop it

### Destructive operations

Ask first: `rm -rf`, `git reset --hard`, `git clean -fd`, dropping a VM, overwriting a config on a provisioned host.

### Lima (local development)

- `limactl list` for status, `limactl shell <name>` to enter a guest
- Prefer native-architecture guests; cross-architecture guests are emulated and slow
- Verify `limactl` flags against the installed version — `limactl create` takes a template positionally and has no `--os` or `--ip`
- Lima addresses are DHCP-assigned; read them, do not assume them
- Document cleanup: `limactl stop`, `limactl delete`, `limactl prune`
- Changes to `lima/*.yaml` must pass `limactl template validate`, and `limactl template copy --fill <file> -` shows what Lima will actually run
- Lima provision scripts re-run on every boot — keep each one guarded and idempotent
- The guest home is `/home/<user>.linux`, not `/home/<user>`; use `{{.Home}}` in a template and `$HOME` in the guest

### Local LAN work on macOS — discovery truth

The sandboxed Docker Node on Docker Desktop **cannot discover LAN hosts**: Docker's NAT answers discovery probes on behalf of every address, so any Node-side discovery scan (`nmap -sn <LAN>/24`, `arping` sweeps) reports all 256 addresses "up" with sub-millisecond latency. **That result is fabricated** — it has produced false host reports before. Never trust an "up" verdict from a discovery scan through the container, and never present such a list as real hosts.

When a task needs the machine's actual LAN (live hosts, IPs, MACs), work from the Mac — it is the only thing on the physical network:

1. Run `scripts/lan_inventory.sh` — it derives the subnet itself (`ipconfig getifaddr en0`), ping-sweeps, and prints live IPs, MACs, best-effort names, and a ready `targets` array. Manual equivalent: `SUBNET=$(ipconfig getifaddr en0 | cut -d. -f1-3)`, ping sweep, `arp -a -i en0`.
2. Use the Node only for **targeted** scans of hosts already known live — those results are faithful (measured; see [Docker Local Dev](docs/DOCKER-LOCAL-DEV.md)). The Node also refuses discovery scans whose result would be fabricated (`nmap -sn` on a CIDR where every address answered), so a fabricated host list can no longer reach a user.
3. Do not expect hostnames: consumer routers rarely serve reverse DNS, and Bonjour/mDNS browsing can fail when a VPN interface owns the default route. Pull names from service banners instead, and say so when a host's name is unknown.
4. For Node-side ARP discovery on a Mac (hosts that drop all unicast probes), use the bridged Lima Node: `scripts/setup_bridged_node.sh` — the Docker Node cannot do this at all. A VPS Node cannot see any LAN it is not physically on (see [VPS Node](docs/VPS-NODE.md)).

Real ARP-based discovery from the tool side needs the [bridged-guest hybrid](docs/DOCKER-LOCAL-DEV.md#lan-discovery-on-macos--the-bridged-guest-hybrid) or a real Linux Node on the LAN.

## Cybersecurity-Specific Rules

### Tool documentation

- Legal use cases only, against systems the reader owns or is authorised to test
- Scan targets in examples: `127.0.0.1`, or RFC 5737 ranges
- State the authorisation requirement rather than assuming the reader infers it

### Model selection

- Core machines (32GB+ RAM): **Mistral Small 3 (24B)** is the default
- Lima guests and constrained hosts: 7B or smaller — `mistral`, `qwen2.5:7b`, `phi3:3.8b`, `llama3.2:3b`
- Confirm a tag exists (`ollama show <tag>`) before documenting it
- Document memory requirements and context-window implications
- **RAM buys capacity, not speed** — a bigger machine runs bigger models, not faster ones

## Testing

There is no test suite. `npm test` in `servers/src/kali/` and `clients/mshin-cli/` runs `node --check` on the source files — a syntax check, nothing more. It catches a typo; it does not tell you the code works.

So:
- Run `npm test` before committing any change under `servers/` or `clients/`
- Then verify behaviour by hand and write down what you ran
- For MCP changes: start the server, hit `/health`, list tools, call the one you touched
- If you add real tests, add them properly and update this section

## Communication Style

- Technically sharp and direct
- Full sentences with normal pronouns ("I read X", not "Read X")
- Structure first, prose after: tables for comparisons, `A → B → C` for flow, `path/to/file.js:42` for code references
- End with what changed and why, any assumption you did not validate, and open questions

**Avoid:**
- Filler adjectives: "robust", "elegant", "powerful"
- Openers like "Great!" or "Absolutely!"
- Emoji
- Claims of "verified", "tested", or "working" without the evidence
- Restating prior reasoning at length
- Comments in the code narrating your own deliberation

## Common Tasks

### Add a tool to the MCP server

1. Read `servers/src/kali/tools.js` end to end
2. Add the `TOOL_PATHS` entry, the definition, and the handler, following the existing pattern
3. Update the other four locations in [Repo Invariants](#the-tool-list-lives-in-five-places) — including sudoers
4. Start the server and call the tool before committing

### Update documentation

1. Read the file end to end
2. Match its structure and tone
3. Verify every command you add or change
4. Link to other docs instead of duplicating them

### Create a new guide

1. Put it in `docs/`, named UPPERCASE-WITH-DASHES
2. Include: quote, overview, prerequisites, setup, usage, troubleshooting, limitations, changelog
3. Say when the reader should use the full two-machine setup instead
4. Add it to `README.md`, `CONTRIBUTING.md`, and the table at the top of this file

## Limitations and Warnings

**Do NOT:**
- Document or run Kali tools against systems the reader does not own
- Commit real credentials
- Assume network connectivity, sudo, or systemd without checking
- Change hardware sizing recommendations without data
- Push to protected branches without approval

**Remember:**
- Ethics first — this project ships offensive tooling
- Lima local development is for learning and testing, never production
- The two-machine setup is the recommended architecture
