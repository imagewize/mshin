# Model Evaluation Run — 2026-10-21

> *"The Pattern does not change because the loom does. Threads woven on a new frame must still lie true — and the only way to know is to weave, and look."*

The second harness-driven model comparison, and the first against the **sandboxed Docker Node** (0.19.0): same harness, same case set, same models — different loom. The 2026-10-20 baseline ran against a Lima guest where tools executed as root on the guest's OS; this run drove the container in its capabilities-limited jail, over the bridge-network override, with bearer-token auth. The question it answers: did the sandbox change what the models can do?

---

## Overview

- **Harness:** `clients/mshin-cli/eval-harness.js`, case set
  `clients/mshin-cli/eval-config.model-comparison.json` — unchanged from the
  baseline run.
- **Node:** the `mshin-node` Docker container on Docker Desktop (macOS), via
  `configs/compose.yaml` + `configs/compose.local.yaml` — bridge network with
  `:3000` published, `cap_drop: ALL` + `NET_RAW/NET_ADMIN`, read-only rootfs,
  bearer-token auth (`configs/mshin-node.env`). Verified before the run:
  `/health` answers with all sixteen tools; `nmap` through `tools/call` returns
  real scan output.
- **Ollama:** native on the 16GB M1 Pro authoring host
  (`http://localhost:11434`).
- **Models:** `mshin`, `qwen3:8b`, `qwen3:4b` — the same tier as the baseline.
  `qwen3:32b` was not re-attempted; the host ceiling that made it unrunnable
  (see 2026-10-20) has not changed.

### What changed since 2026-10-20

Two environment facts matter for reading the numbers:

1. **`127.0.0.1` inside the Node is now the container**, not a guest OS. The
   baseline scanned a guest whose localhost had sshd (:22) and the Node itself
   (:3000); the container has only :3000. The `chain-with-dependency` case
   therefore still asks the model to find the web server on the non-standard
   port — and both 8B-tier models did, pivoting `nikto` from the failed port-80
   attempt to `http://127.0.0.1:3000`.
2. **Tool calls now cross the bridge/published-port path.** `nikto`'s 8137
   requests through the override were measurably slower than the guest-local
   path (`chain-with-dependency` rose from ~68 s to ~105–107 s for both 8B-tier
   models). Scores are unaffected; wall time is not comparable between runs for
   that case.

## Findings

| Model | Overall | Verdict |
|-------|---------|---------|
| `mshin` (persona, qwen3 8.2B base) | 4/4 PASS | Unchanged from baseline: chains, pivots, reports honestly; 5.2–106.8 s per case; context high-water 902 tokens |
| `qwen3:8b` | 4/4 PASS | Unchanged from baseline and indistinguishable from the persona, as expected (same weights); 5.3–104.4 s per case |
| `qwen3:4b` | 2/4 | Still below the bar. `chain-with-dependency`: fabricated output blocked by the backstop (same failure class as the baseline). `recon-chain`: Run FAIL — an MCP request timeout (`-32001`) killed the case while the model was making an exploratory `dnsenum` call; `nmap` was never reached |

**Verdict: the sandbox introduced no regressions on the tier that matters.**
The 8B tier passes all four cases with zero narrated calls and zero fabricated
outputs, at context high-water marks within a few tokens of the baseline
(902 vs 947). The container is a drop-in Node for the harness.

The `qwen3:4b` `recon-chain` failure is the one number that moved (3/4 → 2/4),
and it is honest to say its cause is **not established**: the timeout hit during
a `dnsenum` call — a tool the model chose beyond the expected set, doing DNS
work over the container's NAT path. Model choice or container path, either way
it is a 4B-only failure on a model already rejected by the baseline; nothing in
it indicts the sandbox. Re-running the case against a bare-metal Node with the
same model would separate the two factors if it ever matters.

```bash
  node eval-harness.js -f md -v eval-config.model-comparison.json
```

this run — transcripts and `AgentMemory` are run state, not source; curated
records are committed deliberately, as this file is).
